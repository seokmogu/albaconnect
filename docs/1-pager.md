## 한 줄 요약

알바몬 데이터레이크 실측 비율(강남구 사업주 18,740 : 활성 공고 33,568 : 이력자 60만+)을 0.0167배로 축소한 312 사업장 · 624 공고 · 9,950 구직자 규모의 위치 기반 알바 매칭 시뮬레이터와, 구인자·구직자·관리자 3개 시점의 웹 화면.

---

## 왜 하는가 (Problem)

- AlbaConnect 매칭 알고리즘(거리·평점·직종·신뢰도·가용성·활동성 6요소 가중)이 **실제 규모에서 어떻게 동작하는지 검증할 환경이 없다**.
- 백엔드(Fastify+PostGIS)는 schema 정합성 부채로 풀스택 기동이 어렵다.
- 매칭 결과를 **이해관계자(구인자/구직자/운영자)별 시점**으로 보여줄 화면이 없어, 알고리즘의 의사결정을 설명하기 어렵다.

## 무엇을 만들었나 (What)

| 영역 | 산출물 |
|------|--------|
| 데이터 | 강남구 312 사업장 / 624 공고(LLM 생성) / 9,950 구직자(LLM 생성) |
| 매칭 엔진 | 6요소 가중 스코어링 + LLM 워커 수락 판단 → dispatch 624건, 매칭률 98% |
| 관리자 화면 | `/sim/admin` — 라이브 지도, KPI, 매칭 라인, dispatch 로그 |
| 구인자 화면 | `/sim/employer/[id]` — 공고 진행상황, 매칭 워커, 수락 사유 |
| 구직자 화면 | `/sim/worker/[id]` — 매칭 알림, 진행 일감, 정산 |

## 무엇이 빠졌나 (Gap — 이 문서가 다루는 신규 요구)

> ⚠️ **현재 화면은 전부 "관리자가 남의 페이지를 들여다보는" 구조다.**
> 구인자/구직자가 **본인 시점으로 로그인해 자기 정보만 보는 마이페이지**가 없다.

이 PRD는 위 Gap을 메우는 **마이페이지(My Page) 기능**을 P0로 정의하고, 기존 관제 UI를 P1 유지보수 범위로 둔다.

## 성공 기준 (Success)

- 구인자/구직자가 자기 시점 진입점에서 **본인 데이터만** 보는 마이페이지 동작
- 매칭 시뮬레이션 재현성 (동일 시드 → 동일 결과)
- 매칭률·평균 매칭 시간이 관제 화면에서 실시간 확인 가능

## 범위 밖 (Out of Scope)

- 실제 인증/로그인 시스템 (시뮬이므로 ID 기반 진입)
- 결제·정산 실제 연동 (토스 stub)
- 분쟁/노쇼 시뮬 (Phase 4 별도)
